# Discord コンシェルジュ型チケットBOT / VL-0004 / v0.2.1

Python 3.10以上、discord.py 2.7.1。旧版の接続・通常相談の作成とCloseは利用者が確認済みです。v0.2.1追加機能と第22条の実機テストは未確認です。

## 起動

1. `python -m pip install -r requirements.txt`
2. `.env.example`を参考に環境変数を設定してください。`.env`を自動読込する機能はありません。
3. `python bot.py`
4. サーバー管理者が `/ticket_panel` でパネルを設置します。スタッフは `/ticket` からも利用できます。

Discord Developer PortalでServer Members IntentとMessage Content Intentを有効にしてください。
招待時はbotとapplications.commandsスコープを使用します。BOTにはAdministratorを与えず、対象カテゴリでManage Channels、Manage Roles（権限上書きの管理）、View Channel、Send Messages、Embed Links、Read Message History、Attach Filesを与えてください。通常ログを使う場合、ログチャンネルでも閲覧・送信・ファイル添付を許可します。

## 環境変数

- `TICKET_ENV`: `test`でテスト用担当ロール、`production`で本番用担当ロール。未設定は既存動作を維持して`production`。それ以外は起動を中止します。
- `DISCORD_TOKEN`: BOTトークン。チャットやGitへ貼り付けないでください。
- `GUILD_ID`: 稼働するサーバー1個のID。
- `TICKET_CATEGORY_ID`: 新規チケットを置くカテゴリID。
- `STAFF_ROLE_IDS`: チケットを作成できるスタッフロールID。複数はカンマ区切り。必須です。
- `TICKET_LOG_CHANNEL_ID`: 通常相談のログ転送先。0または未設定で無効。
- `TICKET_DB_PATH`: SQLiteファイルの保存場所。バックアップとアクセス制限が必要です。
- `MAX_OPEN_TICKETS`: 相談者1人の同時チケット数。既定3。保管済みは数えません。
- `TICKET_REMIND_MINUTES`: 未対応通知の待機時間・再通知間隔（分）。既定60、0で無効。1分ごとに対象を走査します。

担当ロールは仕様指定の10窓口を`DESKS`に登録済みです。スタッフの入力はEmbedに表示し、任意メンションの通知は抑止します。チャンネル名・トピック・監査理由には相談内容や当事者情報を含めません。

## プライバシーと第22条

- `@everyone`に閲覧拒否、BOT・相談者・担当ロールにのみ明示的な許可を付けます。カテゴリの上書きはコピーしません。
- 緊急相談は、本人だけに表示されるメンバー選択メニューで当事者を1人選び、その後に相談内容フォームを開きます。「当事者を指定せずに進む」も選べます。IDの手入力は不要です。作成時に選んだ当事者をサーバーから再取得し、退出済み等の場合は作成を止めます。
- 当事者個人には`view_channel=False`を設定します（`read_messages`の別名）。担当ロールの許可より個人拒否が優先します。
- **Discordの所有者・Administratorは権限上書きを無視できます。** 全チケットについてこの例外があります。当事者が該当する緊急相談は、内容を投稿せず作成を中止します。
- 緊急相談では担当ロール名を表示しますが、除外当事者への通知を避けるためロールpingを無効にしています。
- 緊急相談は共通ログへ転送しません。通常相談のログも、元チケットより閲覧範囲が広い場合は転送せず削除を中止します。Server Members Intentとメンバー一覧取得の権限が必要です。
- 共通ログに通常相談を集める場合、部門ごとの閲覧分離が崩れないよう注意してください。このベースは厳しい閲覧範囲照合を行うため、構成次第ではログ転送を拒否します。
- ログはテキスト・Embed内容・添付URLのみです。画像や添付ファイル本体は保存しません。添付URLの永続性は保証しません。
- ログ転送の失敗・容量超過時はチャンネル削除を中止します。ログ無効時、および緊急相談の完全削除は内容を外部保存せず削除します。Closeは削除せず元のチャンネルに保管します。
- BOT自身・他のBOT・サーバー管理者からの閲覧を一律に防げる機能ではありません。管理者、権限編集者、BOT実行環境の管理者を信頼することが前提です。
- 作成後のロール変更・管理者昇格・権限の手動編集は新たなアクセスを生み得ます。本番ではDiscord側の権限変更監査も運用してください。

## 再起動・運用上の制限

作成パネルとCloseボタンは永続Viewです。相談先メニューと削除確認は短時間で失効します。
SQLiteはチケットID・相談者ID・窓口・除外IDに加え、対応状態・受付担当者・通知時刻・権限更新の進行状態を記録します。相談本文はDiscord内にだけ投稿します。通常相談の明示的な完全削除時のみ、任意設定のログ転送があります。
**単一BOTプロセスで稼働してください。** 複数プロセスの排他制御や高可用性は未実装です。
ネットワーク断やプロセス強制終了がチャンネル作成直後に発生すると、空のチャンネルが残ることがあります。カテゴリとSQLiteの照合を運用に含めてください。
カテゴリ上限、担当ロール消失、APIエラー時は利用者に一般的なエラーを返します。生の例外や相談本文を運用ログへ出しません。
SQLiteと閉鎖ログの保管期限・削除規程・バックアップは別途決定してください。

## v0.2.1の追加機能

- **受付／解除**：現在の担当部門のメンバーが受付すると「対応中」、同じ担当者が再度押すと「未対応」に戻ります。別の担当者の受付は上書きしません。相談者自身と除外当事者は受付できません。
- **対応状況**：ボタン、またはチケット内の`/ticket_status`で最新の状態・窓口・担当者を本人だけに表示します。初期メッセージの状態は自動書き換えしません。
- **保管・再開**：Closeの確認後は「完了・保管中」とし、相談者・担当部門の通常投稿とスレッド投稿を停止します。相談者個人には閲覧拒否を付け、担当ロールを兼任していても非表示にします。担当部門の閲覧は維持し、カテゴリ移動は行いません。担当部門が「再開する」を押すと未対応に戻り、相談者の閲覧・投稿を復元します。保管後の再開・完全削除は相談者本人以外の担当部門が行います。相談者がDiscord所有者・管理者の場合は非表示を強制できないため、完了処理を中止します。担当者が交代して受付を解除できない場合も、保管後に相談者本人以外の担当部門が再開して受付をリセットできます。
- **完全削除**：保管済みのチケットで`/ticket_delete`を実行し、確認した場合のみ削除します。通常ログの送信失敗や閲覧範囲の不一致では削除を中止します。保管自体はログへ転送しません。
- **未対応通知**：チケット内だけで、閲覧可能な担当者本人を最大20人までメンションします。相談者・当事者・BOTは通知対象外です。ロール通知・DM・共通チャンネル通知は使いません。受付済み・保管済みは通知しません。BOT停止中には通知できず、再起動後に期限超過分を確認します。送信直後の強制終了では通知が重複する場合があります。
- **窓口変更**：相談者または現在の担当部門が変更先を提案できます。チケット内の確認で相談者本人が**過去の相談・添付を含む全履歴の共有**を承認した場合のみ、担当ロールの閲覧許可を入れ替えます。拒否・失効時は変更しません。申請後に状態が変わると再申請が必要です。元の担当者がすでに見た内容・取得済みのコピーは取り消せません。
- **第22条の継承**：窓口変更・保管・再開でも除外IDを保持します。一度緊急相談として扱ったチケットは、通常部門へ移しても共通ログへ転送しません。変更先に相談者・当事者以外の担当者がいなければ変更しません。通常相談から緊急相談へ変更しても、新たな当事者の指定は追加されません。当事者の指定が必要なら、最初から緊急相談として作成してください。
- **設定チェック**：管理者用`/ticket_check`でカテゴリ、BOTの権限、担当ロールの存在・順位、スタッフロール、メンバー一覧取得、任意ログ送信権限を確認します。チケットごとの実際の非公開性は実機テストが必要です。
- **既存チケット**：旧版で作ったチケットの操作ボタンは`/ticket_controls`で再表示できます。旧Closeボタンも保管動作に切り替わります。

## 更新と障害復旧

1. BOTを停止し、`tickets.sqlite3`（DBパスを変更している場合はそのファイル）をバックアップします。トークンはGitへ登録しません。
2. 新しい`bot.py`を反映して起動します。既存SQLiteの列は自動追加され、既存チケットの相談者・窓口・当事者を維持します。旧版のチケットは「未対応」として移行します。
3. MWSのpullがローカル変更で失敗する状態は、この更新だけでは修復されません。その場合はGitHubの最新版`bot.py`をエディタで置換してください。環境変数とDBを保持します。
4. 権限変更はDiscord APIとSQLiteを一度に確定できないため、承認済みの目標をDBへ先に記録します。途中で停止・APIエラーが起きると「権限更新の確認待ち」とし、他の操作を止めます。元のDiscord権限が残っている場合があります。
5. 管理者が該当チャンネルで`/ticket_recover`を実行すると、**すでに承認された変更**を再試行します。勝手に別部門へ共有する機能ではありません。ロール消失・相談者の退出・当事者の管理者昇格等を解決できなければ、更新を続行しません。必要に応じDiscord側の権限を管理者が確認してください。
6. 保管済みを再開するときも同時チケット上限を確認します。保管チャンネルはサーバーのチャンネル数上限を消費するため、保管期間は運用で決定してください。

## 自動テスト

```sh
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Discordへ接続せず、実際のdiscord.py権限計算とAPIモックで検証します。実機テストの代わりにはなりません。

## 導入前チェック

- 通常相談：相談者と担当者は見える、無関係スタッフは見えない。
- 緊急相談：担当ロールを持つ当事者でも見えない。
- 緊急相談：管理者/所有者が当事者の場合は内容を投稿しない。
- 作成権限なし、無効ID、ロール消失、担当者不在時の拒否。
- Closeの権限、確認キャンセル、同時操作、ログ転送失敗時の削除中止。
- 再起動後のパネル/Close操作とSQLiteの保持。
- 全窓口の実ロールIDと対象カテゴリをテスト用サーバーで確認する。

### v0.2.1適用範囲

この版で完了・保管する時点に相談者の閲覧拒否を設定します。旧版ですでに保管済みのチャンネルの権限は自動変更しません。対象は担当部門がいったん再開し、再度保管してください。保管後に相談者へ管理者権限を付けた場合などはDiscordの仕様により閲覧を防げません。
